# 가져오기

> ⭐ **이 파일에는 «무엇을 하는 일인가»만 있다.** 노하우(증상 표 · 판정 기준)는 두뇌가 내려준다.

⭐ 쓰는 분이 늘 처음부터 야간비행을 쓰는 것은 아니다 — 이미 만들던 중인 제품도
야간비행을 설치할 수 있어 · 이런 경우에도 필요한 걸 다 가져와서 채울 수 있어?」

## 언제 하나

첫 대화인데 이미 만들던 제품이다 — 커밋이 있거나, 화면 파일이 있거나, 기획 메모가 있다.
`0-진단`으로 컴퓨터를 점검한 «뒤»에 한다.

**기록이 이미 있어도 한다** — 대화 끝 검사(`lint_import`)가 «코드가 쌓인 앱인데 조종석 칸이 비어 있습니다»라고 알리면 그때다.
⛔ 첫 대화에만 시키면, 그 전부터 기록이 있던 앱은 한 번도 가져오지 않는다.

```bash
"${CLAUDE_PLUGIN_ROOT}/bin/ledger.sh" 가져오기 시작
```

## 칸마다 — 코드에서 찾아 채운다

| 칸 | 어디서 찾나 | 적는 명령 |
|---|---|---|
| 지금 단계 | 출시했나 · 시험이 있나 · 화면이 다 있나 | `ledger.sh 단계 "<번호>. <이름>"` |
| 제품 이름 | 앱 표시 이름 · 스토어 설정 | `ledger.sh 앱설정 앱이름 "<이름>" 코드` |
| 기획 표 | README · CLAUDE.md · 기획 메모 · 스토어 설명 · 정한 것 기록(누구를 위한 것 · 무엇을 하고 안 하나 · 이름 · 파는 곳 · 가격) | `ledger.sh 기능추가 1 "<묶음>" "<항목>" …` → 항목마다 `ledger.sh 세부상태 "<묶음>" "<항목>" 완료 "<정한 내용 (근거)>"` |
| 검증 표 | 조사 문서 · 경쟁 앱 비교 · 정한 것 기록의 근거 | `ledger.sh 기능추가 2 "<묶음>" "<항목>" …` → `세부상태 … 완료 "<결론> — <근거 이름>: <값> · <근거 이름>: <값> (출처)"` |
| 설계 표 | 설계 문서 · 화면 목록 · 넣은 기능과 뺀 기능 · 정한 것 기록 | `ledger.sh 기능추가 3 "<묶음>" "<항목>" …` → `세부상태 … 완료 "<정한 내용 (근거)>"` |
| 기능 표 | 화면 파일 · 서버 함수 · 문서 | `ledger.sh 기능추가 4 "<기능>" "<세부기능>" …` |
| 만들어 둔 기능 | 코드에 있고 돌아가는 것 | `ledger.sh 설치전 "<기능>" "<세부기능>" "<근거 — 파일 · 통과한 시험>"` |
| 화면 흐름 | 화면 파일 · 화면 이동 코드 | 3-설계 스킬의 «화면 흐름» 명령 — 끝에 `화면일` 로 «하는 일»마다 지나는 화면 차례를 적는다 |
| 기능끼리 영향 | 두 기능이 같은 자료 · 같은 화면을 쓰는 코드 | `ledger.sh 영향 "<기능>" "<같이 바뀌는 기능>" "같은것을쓴다: <무엇>" 코드` · 안 엮이면 `ledger.sh 독립 "<기능>" "<이유>"` |
| 기능마다 상태 | 결제됨 · 만료 같은 상태 값 | `ledger.sh 상태 "<기능>" "<상태>" "<갈 수 있는 곳>" 코드` |
| 정한 것 | 문서 · 커밋 글에 적힌 결정 | `ledger.sh 결정 …` — 아래 «결정은 다섯 칸 + 세 표지» 꼴 그대로 |
| 만드는 법 | 코드가 쓰는 방식(결제 · 로그인 · 저장) | `ledger.sh 표준 "<방식>" "<어느 파일>" 코드 "<기능>"` |
| 출시 절차 질문 | 결제 · 로그인 · 플랫폼 코드 | `ledger.sh 앱설정 <플랫폼·돈받기·기능> "<값>" 코드` |
| 출시 상태 | 스토어 주소 · 출시 커밋 · 심사 메일 | `ledger.sh 앱설정 출시상태 "<출시 전 · 심사 중 · 출시함 — 근거>" 코드` |
| 읽은 문서 | README · CLAUDE.md · AGENTS.md · docs/ | `ledger.sh 앱설정 읽은문서 "<문서 이름들 — 문서마다 정한 것 n건>" 코드` — 읽은 문서에서 나온 결정은 «정한 것» 칸에 적는다 |

### 명령의 꼴 — 거절되기 전에 알아 둘 것

가져오기 시험(2026-10-25, 기록을 지운 앱 복사본)에서 거절된 열두 번이 모두 아래 자리였다.

- **단계 이름**: `0. 진단` · `1. 기획` · `2. 검증` · `3. 설계` · `4. 개발` · `5. 확인` · `6. 출시` · `7. 수정` · `8. 출시후`.
  `0. 진단`을 먼저 적고, **지금 단계는 맨 마지막에** 적는다 — 마지막 줄이 지금 단계다.
  ⛔ `4. 개발` 이후는 화면 흐름과 기능끼리 영향이 «먼저» 있어야 받는다. 순서: 기능 표 → 설치전 → 화면 흐름 → 영향 → 단계.
- **화면 문구(`--화면`)와 결정의 `--값`은 명사구로** 쓴다 — «~다 · ~습니다»로 끝나면 거절된다.
  예: «세 화면이 같은 거리 값을 씀» (O) · «세 화면이 같은 거리 값을 쓴다» (X).
- **`기능추가 4`의 4**는 그 기능이 사는 단계(4 = 개발)다. 앱의 기능은 4에 둔다.
- **기획 · 검증 · 설계 표**(1 · 2 · 3)는 «정한 것»을 묶음과 항목으로 나눈 표다. 항목의 «정한 내용»은 `세부상태 … 완료 "<내용>"` 의 넷째 칸에 쓴다 —
  조종석이 그 단계를 열면 이 글이 보인다. 내용 끝 괄호에 근거(문서 이름 · 파일:줄 · 결정 날짜)를 둔다.
  찾지 못한 항목은 만들지 않는다. 그 단계 전체를 못 찾았으면 `가져오기 없음 "<칸>" "<이유>"`.
  ⭐ **검증 표만 꼴이 하나 더 있다** — 맨 앞에 결론 한 줄, « — » 뒤에 근거를 «이름: 값»으로 « · » 로 잇는다.
  조종석이 결론을 위 상자로, 근거를 짝으로 그린다. « — »가 없으면 결론 상자 없이 근거만 줄로 보인다(지어내지 않는다).
  예: `월구독만 파는 가계부는 없다 — 잰 앱: 한국 가계부 12개 · 월구독 가격: 1,000~2,900원 (docs/research/04.md · 2026-09-30)`
- **이름에 가운뎃점(·)을 쓰지 않는다** — 기능 · 세부기능 · 화면 이름. «와» · «과»로 풀어 쓴다.
- **영향 · 표준**에는 화면 문구가 필요하다: 끝에 `--화면 "<사용자가 겪는 일>" --종류 "사용자에게 보이는 것"`
  (사용자가 아무 차이도 못 겪는 일이면 `--종류 "안 보이는 작업"`만).
- **결정**은 다섯 칸 + 세 표지다:
  `ledger.sh 결정 "<정한 것>" "<근거 — 문서 · 커밋>" "<전제 — 이것이 바뀌면 다시 본다>" "<주제 한 낱말 또는 빈 칸>" "<묶임>" --항목 "<무엇을>" --값 "<어떻게>" --조건 "<다시 볼 조건 — 화면 문구>"`
  · 다섯째 칸 «묶임»은 `돈|시간|법|못되돌림|없음` 중 하나로 시작한다. 코드 · 문서에서 비용 근거를 못 보면 `없음: 가져오기 — 비용 근거를 못 봄`.
- **앱설정 값**: 플랫폼 `iPhone · 안드로이드 · 웹 · 스토어에 안 낸다 · 모름` · 돈받기 `앱안에서 · 밖에서 · 안받는다 · 모름` ·
  기능은 값을 아무거나 넣으면 고를 수 있는 목록이 돌아온다.
- **상태의 갈 곳**은 이미 적은 상태 이름이거나 «끝»이다. 여럿이면 쉼표로(`"사용 중,만료"`). 더 갈 곳이 없으면 «끝».
  같은 상태를 다시 적으면 덮어쓴다 — 갈 곳을 바꿀 때는 갈 곳 전체를 다시 적는다. 갈 곳이 아직 안 적은 상태면 그 상태를 먼저 적는다.
- **앱설정**은 한 번에 값 하나 · 같은 축을 여러 번 부르면 쌓인다(기능처럼 여럿인 축).
- **결정의 근거**: 문서 · 커밋 글 · 코드 주석에 «왜 이렇게 하나»가 적힌 것. 근거 칸에 그 자리(파일:줄)를 적는다.
- **README와 코드가 다르면 코드를 따른다** — 다른 곳은 «정한 것»이 아니라 그 차이를 사람에게 알린다.
- **화면 짧은 이름**은 띄어 쓰지 않아도 된다(`홀지도`) — 사람이 읽는 이름은 `화면이름`으로 따로 적는다.
- **화면상태**의 «다음으로 가는 때»가 없으면 빈 칸(`""`)으로 둔다.
- 앱 화면이 아닌 것(전화기 기본 수신 화면 · 메일)도 사용자가 거쳐 가면 화면으로 적는다 — 메일은 `화면종류 … 메일`.

이 앱에 그 칸이 없으면(예: 화면 없는 서버) 이유와 함께 적는다:

```bash
"${CLAUDE_PLUGIN_ROOT}/bin/ledger.sh" 가져오기 없음 "<칸>" "<이유>"
"${CLAUDE_PLUGIN_ROOT}/bin/ledger.sh" 가져오기          # 칸마다 지금 상태
```

## 확인받기

1. 다 채우면 사람에게 짧게 보인다 — 지금 단계 · 기능 표 · 화면 흐름.
2. 코드에 있고 돌아가는 세부기능은 `설치전` 으로 «완료»가 된다. ⛔ «확인 필요»로 넣지 않는다 —
   이미 돌아가는 제품의 기능이 사용자의 «지금 하실 일»을 덮는다.
3. 사람이 «아니다»라고 한 세부기능만 `세부상태` 로 고친다.

## ⛔ 못

1. **찾지 못한 칸을 빈 채로 두지 않는다** — 빈 칸은 «없다»로 읽힌다. 찾았거나, «없음»과 이유를 적거나 둘 중 하나다.
   대화 끝 검사(`lint_import`)가 남은 칸을 알린다.
2. **근거 없이 완료로 적지 않는다** — 코드의 자리(파일:줄)나 통과한 시험이 있어야 `설치전` 을 부른다. 화면에서 안 쓰이는 코드는 넣지 않는다.
3. **앱 코드를 고치지 않는다** — 가져오기는 읽기만 한다.
4. **결정의 근거를 지어내지 않는다** — 문서 · 커밋에 적힌 것만. 없으면 «정한 것»은 비워 두고 «없음» 이유를 적는다.
